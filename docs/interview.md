# Agent Interview Notes

# Part 1：项目相关问题（Project）

## P1：Prompt是什么？你在项目中怎么用的？

**回答（1分钟版本）：**

“Prompt是输入给大语言模型的指令文本，用来引导模型完成特定任务。它的核心作用是在推理阶段控制模型的行为和输出，而不用重新训练模型。

在TripMate中，我主要通过System Prompt约束Agent行为，包括定义Agent角色、可调用工具、Action格式以及决策规则。例如要求模型根据用户需求选择tool、need_information或者generate_plan，并通过JSON格式输出Action，方便后端解析执行。

好的Prompt = 角色 + 任务目标 + 输出格式约束 + 边界行为（比如不确定时怎么办）。”


## P2：System Message和User Message有什么区别？为什么重要？

**回答（1分钟版本）：**

“在调用LLM API时，Messages数组至少包含两种角色：

System Message：设置模型的底层行为规则，相当于给模型一个‘人设’和‘操作手册’，在整个对话中持续生效。User Message：用户每次提出的具体需求或问题，是模型当前要响应的内容。

两者的核心区别是稳定性和变化性——System是固定不变的底座，User是每次不同的输入。

在TripMate项目中，System Prompt定义‘你是旅行助手，输出包含行程、美食、交通、预算’，这部分对话开始后就不再变动；User Message则是用户每次输入的目的地、天数、预算，动态变化。

这个设计还有一个好处：后续做多轮对话时，System始终保持模型的行为边界，不会因为上下文变长而‘角色漂移’。”


## P3：如果未来增加RAG，你会如何设计？

Embedding是将文本转换为高维浮点数向量的技术，使得语义相近的文本在向量空间中距离更近。同一个词在不同语境下的向量会不同，这是它与传统词向量的关键区别。

在Agent项目里，Embedding最核心的用途是RAG检索。具体流程是：

1. 把旅游攻略文档切分成片段，每个片段通过Embedding模型转成向量，存入向量数据库
2. 用户提问时，同样把问题转成向量
3. 在向量库里做余弦相似度检索，找到语义最相关的3-5个文档片段
4. 把这些片段拼接到Prompt里，让LLM基于真实资料回答

这样就把‘闭卷考试’变成了‘开卷考试’，大幅降低幻觉。

常用的Embedding模型有OpenAI的text-embedding-3-small、BGE、智谱的Embedding系列。如果后续为TripMate增加RAG，我会考虑使用BGE等中文Embedding模型，因为其开源且适合中文语义检索场景


## P4：LLM API调用和本地部署怎么选？你的项目为什么选API？

“我这样选：从三个维度权衡——成本、数据安全、灵活性。
API调用的优势是零硬件成本、按token付费、能直接用最新最强的模型（比如DeepSeek），适合个人项目和快速验证。劣势是数据要上传第三方，隐私可控性差，长文本场景成本会累积。
本地部署的优势是数据完全在内网、长期使用成本可控、延迟更低。劣势是需要GPU服务器（至少A100或4090级别），前期投入数万到数十万，运维复杂，模型能力限于开源模型。
在TripMate项目中我选择DeepSeek API，原因有三：第一，项目处于MVP验证阶段，我要快速迭代产品形态；第二，DeepSeek中文能力强、成本低；第三，求职项目需要展示‘能调用真实API做出可运行产品’的工程能力，而不是纯理论研究。
如果未来做企业级部署，或者处理用户隐私数据，我会考虑切换为本地Qwen或Llama部署，架构上保持API可插拔。”

## P5：你的项目如何保证LLM输出可靠？

项目中有两个结构化约束：AgentAction主要约束Agent内部决策流程，TravelPlan主要约束最终业务输出。
LLM输出Action JSON后，会经过Pydantic验证，确保action、tool、arguments等字段符合预期。
相比直接解析字符串，这种方式提高了Agent流程稳定性，避免LLM自由输出导致流程错误。

## P6：Agent和普通LLM应用有什么区别？

回答：

普通LLM应用：
用户输入 → LLM → 输出

Agent：
用户目标 → LLM规划 → Tool调用 → 环境反馈 → 下一步行动

核心区别：
LLM应用主要生成内容，
Agent主要完成任务。

## P7：为什么你的项目需要Agent？
回答：

旅行规划不仅需要生成文本，还涉及实时天气、交通、景区信息等动态数据。传统LLM只能依靠参数记忆生成内容，而Agent可以根据任务需求主动调用外部工具获取信息，再结合LLM完成规划。

## P8:你的Agent具体是怎么实现Tool Calling的？

回答：

我的项目没有直接依赖第三方Agent框架，而是自己实现了一个简化版Tool Calling流程。首先通过Prompt告诉LLM当前可用工具以及参数格式，LLM根据用户需求输出结构化JSON Action，例如工具名称和参数。然后由后端Agent模块解析这个JSON，通过Tool Registry找到对应Python函数并执行，将执行结果作为Observation重新输入LLM，最后由生成模块输出旅行方案。

## P9：为什么不用LangChain，而自己实现Agent？

回答：

LangChain等框架提供了成熟的Agent抽象，但为了理解Agent底层机制，我在项目初期选择自己实现核心流程，包括工具注册、工具选择、执行和结果回传。这样可以明确理解LLM和外部工具之间的交互方式。后续如果扩展复杂流程，可以考虑使用LangGraph等框架管理状态。

## P10:你的项目里面LLM到底负责什么？代码负责什么？

我采用LLM负责非确定性决策，代码负责确定性执行。LLM负责理解用户意图、决定是否调用工具以及生成规划方案；代码负责API调用、工具执行、数据校验和流程控制，这样可以降低幻觉风险。这种设计可以避免把所有逻辑交给LLM，提高系统可控性。

## P11：为什么Observation很重要？

Tool执行结果不会直接返回给用户，Observation表示Agent获得了新的环境信息，Planner根据Observation重新规划下一步Action。Observation相当于Agent与外部环境交互后的反馈，它让LLM知道工具执行结果，并根据新信息决定下一步行动。

## P12：Planner和TravelPlan为什么分离？

Planner负责决策,TravelPlan属于业务对象。
因此我将Agent决策和业务对象生成拆分。
Planner负责：决定什么时候生成。
chat_with_llm负责：输出符合Pydantic约束的TravelPlan。
这样职责更加清晰，也方便以后扩展不同输出类型。

## P13：你的Agent如何实现多轮对话？

之前的Agent每次请求都是独立执行的：用户输入 → Agent → 回答，无法理解之前的信息。
为了支持多轮任务，我增加了Session Memory模块，通过session_id区分不同对话，并保存当前会话中的历史信息。
当前流程是：用户输入 → 保存当前消息 → 读取历史上下文 → Planner决策 → Tool调用 → 保存结果 → 生成回答
Memory中保存用户消息、Tool Observation和Agent回复。
例如，第一次对话用户问：“成都天气怎么样”，Agent调用天气API获取结果。第二次用户接着问：“我准备玩5天”，即使用户没有再次输入地点，Agent也可以根据历史上下文理解当前仍然是在讨论成都旅行。


## P14：你的Agent如何实现Memory？

我采用Conversation Memory + State Memory的结构来实现Agent的Memory机制。
其中，Conversation Memory负责保存完整的历史对话信息，包括用户输入和Agent回复，并通过session_id区分不同用户会话。在每次请求时，Agent可以读取对应Session的历史上下文，理解当前多轮对话。
State Memory则负责结构化保存任务中的关键信息，例如旅行目的地、天数、预算和出发日期等，用于辅助Agent完成更复杂的任务。
目前系统通过Conversation Memory保存上下文，通过State Memory维护当前任务状态，两者结合支持Agent进行连续的旅行规划。


## P15：为什么Agent需要同时设计Conversation Memory和Task State Memory？

一开始我的设计比较简单，只保存Conversation Memory，也就是把用户和Agent之前的聊天记录保存下来，让Agent根据历史上下文继续对话。
但是实际测试的时候发现，这种方式有一个问题：Agent每次都需要重新从历史消息中提取当前任务状态。
比如用户先说“我想去成都玩5天”，后面又补充“预算5000”。对于人来说，可以很自然地知道这两个信息属于同一个旅行计划，但是对于Agent来说，如果只依赖聊天记录，就需要重新分析之前的所有上下文，随着对话变长，可能出现信息遗漏或者理解错误。
所以后续我增加了Task State Memory，把旅行任务中的关键信息单独结构化保存，比如目的地、旅行天数、预算和出发日期。
这样两个Memory各自负责不同的事情：Conversation Memory负责保存完整对话过程，让Agent理解用户上下文；Task State Memory负责保存当前任务状态，让Agent可以直接获取规划所需的信息。
这种设计既保留了多轮对话能力，也让Agent在处理复杂任务时更加稳定。

## P16：如何避免 Agent 重复调用同一个工具？

仅依赖 Prompt 告诉 LLM“不要重复调用工具”并不可靠，因为 Prompt 属于软约束，模型仍可能生成重复调用，甚至通过修改 query 参数产生语义相同的重复检索。

项目中在 Agent Runtime 层增加了两级去重机制。第一层使用 executed_calls，根据 tool name + arguments 生成唯一 key，阻止完全相同的工具调用重复执行；第二层使用 completed_tasks 记录已经完成的信息获取任务，例如 retrieve_travel_info 已经返回 available=true 后，将 travel_info 标记为完成，即使后续 LLM 换一个 query 再次请求 RAG，也不会重新执行。

因此 Prompt 负责引导 Agent 的决策，而 Runtime Guard 负责保证关键执行约束真正生效。


## P17：为什么不能只通过 Prompt 控制 Agent 行为？

因为 LLM 的输出具有不确定性，Prompt 中的规则只能降低错误行为发生的概率，不能提供严格保证。

因此项目中将约束分成两类：需要语义判断的行为，例如什么时候查询天气、什么时候使用 RAG，由 LLM 根据 Prompt 决策；必须严格满足的执行约束，例如最大循环次数、完全重复的 Tool Call、已经完成的检索任务，则由程序代码控制。

这种设计能够减少 Agent 对 Prompt 稳定性的依赖，使执行流程更加可控。

## P18：为什么将原来的手写 Agent 循环迁移到 LangGraph？
原有 Agent 已经具备 Planner、Tool Calling、RAG、Web Search 和 Memory 等能力，但执行流程主要集中在 run_agent() 的 for + if + continue 结构中。随着工具数量和 Action 分支增加，流程控制、状态维护和异常处理会越来越复杂。因此我没有重写已有业务能力，而是引入 LangGraph，将 Planner、Tool、计划生成、信息补充和直接回答拆成不同 Node，通过 Edge 和 Conditional Edge 显式描述执行流程，使 Agent Runtime 更容易扩展和维护。

## P19：你的 LangGraph 工作流是怎么设计的？
我使用 AgentState 保存一次 Graph 执行过程中的运行时状态。Graph 从 planner 开始，由 LLM 输出 AgentAction，再通过 conditional edge 根据 action 分流：tool 进入工具节点，执行完成后携带 Observation 回到 planner；need_information 直接返回需要补充的信息；direct_answer 用于天气等简单问答；generate_plan 根据已经获得的用户状态和工具信息生成结构化 TravelPlan。这样形成了 planner → tool → planner 的 Agent 循环，同时让不同结束路径保持清晰。

## P20：LangGraph 的 State 和项目原来的 Memory 有什么区别？
项目中的 TravelState 属于业务状态，用于保存用户跨轮对话中的 destination、days、budget、travelers、preferences 等旅行需求；LangGraph 的 AgentState 属于运行时状态，用于保存 decision、tool_result、executed_calls、step_count 等一次 Agent 执行过程中的信息。目前我没有为了使用 LangGraph 强行替换原有 Memory，而是让 runner 将业务状态组装成 Graph 输入，由 Graph 负责本轮工作流执行。这样两个状态层职责更加明确。

# Part 2：AI基础知识（LLM / Agent）

## K1：为什么LLM可以生成文本？

### 核心：

LLM生成文本的本质是一个自回归语言建模过程。
模型通过大量文本数据进行训练，学习“给定前文，预测下一个token出现概率”的能力。训练过程中，模型不断调整参数，使预测结果尽可能接近真实文本。
在生成阶段，用户输入经过Tokenizer转换成token，模型根据已有上下文计算下一个token的概率，然后选择一个token加入上下文，继续预测下一个token，循环这个过程，最终生成完整文本。
简单来说，LLM并不是提前存储了一句话然后直接拿出来，而是在每一步根据上下文预测最可能出现的下一个token，通过大量token预测组合成最终回答。

#### 追问1：什么是自回归？

自回归就是根据已有内容预测下一个内容。
对于LLM来说，就是根据前面已经出现的token，预测当前应该生成什么token。
例如生成一句“今天的天气很好”，模型不是一次生成整句话，而是：
输入“今天的” → 预测“天气”
输入“今天的天气” → 预测“很”
输入“今天的天气很” → 预测“好”
不断重复这个过程。
GPT这类模型采用的就是自回归生成方式。

#### 追问2：为什么需要Softmax？

Transformer最后输出的是每个token对应的一个分数，也就是logits，但这些分数不能直接表示概率。
Softmax的作用是把这些分数转换成概率分布，让模型知道每个候选token被选择的可能性。
例如预测下一个词时，模型可能得到：
“好”：0.6
“差”：0.2
“热”：0.1
然后根据这些概率选择最终token。
所以Softmax连接了模型输出和token选择过程。

#### 追问3：Temperature有什么作用？

Temperature用于控制LLM生成结果的随机性。
它实际上会调整Softmax后的概率分布。
Temperature较低时，高概率token会更加突出，模型更倾向选择最可能的结果，因此输出更加稳定。
Temperature较高时，不同token之间概率差距减小，低概率token也有机会被选择，因此生成结果更加多样。
实际应用中需要根据场景调整，比如代码生成和事实问答通常使用较低Temperature，而创意生成可以适当提高。

#### 追问4：Top-p是什么？

Top-p是一种采样策略，用于限制模型选择token的范围。
它会按照token概率从高到低排序，然后选择累计概率达到p的候选集合，只在这个集合中进行采样。
例如top-p设置为0.9，模型只会考虑累计概率最高的90%的token。
相比Top-k固定选择前k个token，Top-p更加灵活，因为不同情况下模型的不确定程度不同，候选数量也会动态变化。

#### 追问5：LLM是真的理解文本吗？

严格来说，LLM并不是像人一样理解文本。
它本质上是通过训练数据学习语言中的统计规律和语义关联，在高维空间中形成文本表示。
例如模型知道“苹果”和“手机”经常相关，是因为训练数据中存在大量类似表达。
但是这种能力并不代表模型真正理解现实世界，也不知道生成内容一定正确，所以会出现幻觉。
因此实际应用中需要结合RAG、Tool Calling等方式，让LLM获得外部知识和真实环境反馈。


## K2：Transformer为什么适合LLM？

### 核心：

Transformer适合作为LLM基础架构，主要因为它能够通过Self-Attention机制有效建模token之间的关系，同时具备高度并行和可扩展的特点。
在LLM中，文本首先被转换为token序列，Transformer通过多层Attention和Feed Forward Network逐步学习token之间的上下文关系，最终得到具有语义信息的表示。
相比传统神经网络结构，Transformer的计算方式更加适合GPU并行，并且可以通过增加模型参数、训练数据和计算资源不断提升能力，这也是目前大语言模型能够达到大规模参数量的基础。

#### 追问1：Self-Attention是什么？

Self-Attention的作用是让模型在处理一个token时，能够关注输入序列中的其他token，并根据相关性动态分配权重。具体来说，每个token都会生成三个向量：
Query（Q）：表示当前token想关注什么信息；
Key（K）：表示每个token可以提供什么信息；
Value（V）：表示实际传递的信息。
模型通过计算Q和所有K之间的相似度，得到注意力权重，再对V进行加权求和，得到融合上下文信息后的表示。
简单来说，Self-Attention解决的问题是：当前token应该关注哪些其他token，以及关注程度是多少。
例如一句话：“苹果发布了新的手机，因为它很受欢迎。”模型通过Attention可以学习到“它”指代“苹果手机”。

#### 追问2：Multi-Head有什么作用？

Multi-Head Attention就是让模型同时使用多个不同的Attention头，从不同角度学习token之间的关系。
因为单个Attention只能学习一种关系，而不同的头可以关注不同的信息。
例如：
某些头关注语法关系；
某些头关注语义关系；
某些头关注长距离依赖。
最后多个head的结果进行拼接和线性变换，得到更加丰富的表示。
所以Multi-Head的核心作用是提高模型捕捉不同类型信息的能力。

#### 追问3：为什么比RNN好？

主要有三个原因。
第一，Transformer能够并行训练。
RNN处理序列时必须按照时间顺序逐步计算，前一个状态计算完成后才能计算下一个状态，GPU利用率较低。
而Transformer通过Attention可以一次计算整个序列中token之间的关系，更适合GPU并行。
第二，Transformer更容易捕捉长距离依赖。
RNN的信息需要经过多个时间步传递，距离较远的信息容易丢失。
Transformer中任意两个token都可以直接通过Attention建立联系。
第三，Transformer更容易扩展。
大模型训练需要处理海量数据和参数，Transformer结构简单、计算方式适合GPU，因此能够通过增加参数和数据规模持续提升能力。

#### 追问4：Attention为什么是O(n²)？

因为Self-Attention需要计算序列中任意两个token之间的关系。
假设输入长度是n，每个token都需要和其他n个token计算Attention，因此需要生成一个n×n的Attention矩阵。
所以计算量和序列长度平方相关，也就是O(n²)。
例如：
10个token需要计算100个关系；
1000个token需要计算100万个关系。
这也是为什么长文本处理会成为Transformer的瓶颈，很多研究会尝试稀疏Attention、线性Attention等方法降低复杂度。

#### 追问5：KV Cache是什么？

KV Cache是Transformer推理阶段的一种优化技术。
在生成文本时，模型每生成一个新的token，都需要计算当前token和之前所有token之间的Attention。
如果每次都重新计算之前token的Key和Value，会产生大量重复计算。
因此KV Cache会缓存之前token计算得到的Key和Value，在生成新token时直接复用，只需要计算新的token对应的Q、K、V。
这样可以显著降低生成阶段的计算开销，提高推理速度。
不过KV Cache也带来了显存压力，因为缓存内容会随着上下文长度增长。
这也是很多LLM推理优化研究关注的问题。

#### 追问6：为什么长文本困难？

长文本困难主要有两个原因。
第一是计算复杂度问题。
由于Attention是O(n²)，文本长度增加时，计算量和显存占用都会快速增长。
第二是上下文管理问题。
虽然模型支持更长上下文，但并不意味着一定能够有效利用所有信息。文本越长，重要信息越容易被大量无关内容稀释，模型可能出现信息遗漏。
工程上常见解决方案包括：KV Cache优化推理；RAG只检索相关内容；长文本摘要压缩上下文；稀疏Attention减少计算。


## K3：Token和字符有什么区别？

### 核心：

LLM并不是直接处理文字，而是先通过Tokenizer将文本转换成Token，再将Token转换成模型能够计算的向量。字符是人类理解文本的基本单位，例如一个汉字或者一个字母；而Token是模型处理文本的基本单位，可以是一个完整单词、词的一部分，甚至一个字符。
Token和字符不是一一对应的关系，不同语言和不同Tokenizer会产生不同数量的Token。例如英文中的一个高频单词可能对应一个Token，而生僻词可能会被拆分成多个Token。中文由于没有天然空格分隔，同时词语组合更加灵活，因此通常需要更多Token表示相同长度的信息。
在实际应用中，Token数量会直接影响模型上下文长度、计算成本和API费用。比如LLM所说的8K上下文限制指的是8K个Token，而不是8K个字符；在Agent中，如果Conversation Memory不断累积历史对话，也会导致输入Token增加，因此需要结合State Memory、摘要等方式控制上下文规模。

#### 追问1：BPE怎么工作？

BPE是一种常见的子词分词算法，它的核心思想是通过统计文本中高频出现的字符组合，不断合并生成新的Token。训练阶段，算法从较小粒度开始，例如字符或字节，然后寻找频率最高的相邻组合进行合并，直到达到预设词表大小。
这样可以同时兼顾效率和泛化能力：高频词可以直接作为一个Token，提高处理效率；低频词或者新词可以拆分成多个子词，避免无法表示。GPT系列模型使用的Tokenizer就是基于BPE思想的变体。

#### 追问2：中文为什么token更多？

主要原因是中文和英文的语言结构不同。英文天然有空格分隔，很多高频单词可以直接作为一个Token；而中文没有明确的词边界，需要Tokenizer根据训练数据学习哪些字符组合应该合并。
例如一些常见词可能会作为整体Token保存，但不常见的组合可能会被拆分。因此在表达相同语义内容时，中文通常需要更多Token，这也是中文场景下上下文长度和API成本需要特别关注的原因。

#### 追问3：Token数量为什么影响上下文和成本？

Token数量主要影响三个方面。第一是上下文长度，模型限制的是Token数量，而不是字符数量，因此输入越长，占用的上下文空间越多。第二是计算成本，Transformer中的Attention需要计算Token之间的关系，Token越多，计算量和显存占用越高。第三是API调用成本，大部分模型服务按照输入输出Token数量计费。
对于Agent来说，这个问题更加明显，因为多轮对话会不断积累历史消息。如果不进行控制，可能导致Prompt过长、成本增加，甚至影响模型对关键信息的关注。

#### 追问4：词表大小有什么影响？

词表大小需要在效率和参数量之间进行权衡。词表较大时，一个Token通常包含更多信息，可以减少文本长度，提高处理效率，但Embedding层参数量会增加，同时低频Token可能缺少足够训练数据。词表较小时，模型参数更少，但是文本会被切分成更多Token，导致序列变长，增加计算成本。
因此实际大模型通常选择一个折中的词表规模，在表示能力、计算效率和多语言覆盖之间进行平衡。


## K4：LLM为什么会幻觉？

### 核心：

LLM产生幻觉的根本原因是它的训练目标是预测下一个最可能出现的token，而不是判断信息是否真实。
模型在训练过程中学习的是大量文本中的语言规律和知识模式，但它并没有一个独立的事实数据库，也无法真正判断某个内容是否正确。
因此，当用户询问的问题超出模型知识范围，或者模型对某个信息不确定时，它仍然会根据已有模式生成一个看起来合理的答案，这就可能产生幻觉。
简单来说，LLM擅长生成“合理的内容”，但不一定保证内容“真实”。

#### 追问1：RAG为什么降低幻觉？

RAG通过在生成回答之前引入外部知识检索，降低模型依靠自身参数记忆生成答案的风险。
具体流程是：首先将外部文档切分并转换成向量存入向量数据库；用户提问时，将问题转换成向量进行检索，找到相关内容后，把这些资料加入Prompt，让LLM基于检索结果生成回答。
这样相当于给模型提供了一个实时参考资料，让它从“闭卷回答”变成“参考资料回答”。
不过RAG不能完全消除幻觉，因为如果检索内容错误，或者模型理解和整合资料时出现问题，仍然可能生成错误答案。

#### 追问2：Tool Calling为什么降低幻觉？

Tool Calling降低幻觉的核心原因是让LLM不要依赖参数记忆处理需要实时或者精确信息的问题，而是调用外部系统获取真实结果。
例如用户询问天气，如果直接让LLM回答，它只能根据训练数据中的信息猜测；而通过Tool Calling调用天气API，可以获得当前真实天气，再让LLM基于结果生成回答。
在Agent中，LLM主要负责理解需求和决定是否调用工具，具体的数据获取和计算交给确定性的程序执行。
不过Tool Calling并不能完全解决幻觉，因为模型仍然可能选择错误的工具、生成错误参数，或者错误理解工具返回结果，所以还需要结合结构化输出和程序校验。

#### 追问3：幻觉能否完全解决？

目前不能完全解决。
因为LLM本质上是概率生成模型，即使模型能力很强，它仍然是在预测最可能出现的内容，而不是像数据库一样查询确定事实。
工程上更多是降低幻觉概率，而不是完全消除。
常见方法包括：使用RAG补充外部知识；使用Tool Calling获取实时和确定性数据；通过System Prompt约束模型行为；通过结构化输出和后处理进行校验。
在实际应用中，需要根据任务特点设计可靠性机制，而不是单纯依赖LLM自身能力。


## K5：什么是Agent？

### 核心：

Agent是一种基于LLM的任务执行系统，它的核心区别是让LLM不只是生成文本，而是能够理解目标、规划下一步行动、调用外部工具，并根据执行结果继续调整。
普通LLM通常是一次性的输入输出：
用户输入 → LLM → 生成回答。
而Agent通常是一个循环过程：
用户目标 → LLM决策 → 执行动作 → 获得反馈 → 再次决策 → 完成任务。
其中LLM负责理解和规划，Tool负责提供外部能力，Memory负责保存上下文和状态，Agent框架负责控制整个执行流程。
例如在我的TripMate项目中，用户提出旅行需求后，Agent不会直接生成攻略，而是先判断是否需要查询天气、景点等信息，调用工具获取结果后，再生成最终旅行方案。

#### 追问1：Agent和普通LLM区别？

两者最大的区别是目标不同。
普通LLM主要解决内容生成问题，用户提出问题后，模型直接生成答案。
而Agent解决的是任务完成问题，它需要根据目标主动规划步骤，并与外部环境交互。
例如用户问“成都适合什么时候旅游”，普通LLM可能直接根据已有知识回答；而Agent可以先查询天气、景点开放情况等信息，再结合工具结果生成更准确的建议。
简单来说：LLM负责“回答问题”，Agent负责“完成任务”。

#### 追问2：Tool Calling机制？

Tool Calling的核心思想是让LLM负责决策，让代码负责执行。
具体流程是：首先通过Prompt告诉LLM有哪些工具、每个工具的功能以及参数格式。LLM根据用户需求生成结构化调用信息，例如工具名称和参数。后端程序解析这个结果，调用对应的Python函数或者外部API，然后把执行结果作为Observation返回给LLM，让模型继续决定下一步。
在我的TripMate项目中，就是通过Tool Registry管理工具，LLM输出Action后，由Agent模块找到对应工具执行，例如调用天气API或者景点查询接口。
这样可以避免让LLM直接生成不可靠的信息，把实时数据获取交给确定性的程序。

#### 追问3：Memory设计？

Agent中的Memory主要用于保存和管理任务过程中的信息。
在我的项目中采用Conversation Memory和Task State Memory两层设计。
Conversation Memory负责保存完整历史对话，例如用户输入、工具结果和Agent回复，通过session_id区分不同会话，让Agent能够理解多轮上下文。
Task State Memory负责保存结构化任务状态，例如旅行目的地、天数、预算和出发日期，让Agent不需要每次从大量历史消息中重新提取关键信息。
两者结合可以同时保证多轮对话能力和复杂任务执行稳定性。

#### 追问4：ReAct？

ReAct是一种经典Agent执行模式，全称是Reasoning and Acting。
它的核心思想是让模型交替进行推理和行动：先根据当前状态分析下一步应该做什么，然后执行Action，再根据Action返回的Observation继续判断。
流程类似：Reasoning → Action → Observation → Reasoning。
例如旅行规划中，Agent可能先判断需要查询天气，然后调用天气工具，获得天气结果后，再决定是否调整行程。
ReAct的优势是让模型能够结合外部环境反馈动态调整，而不是一次性生成完整答案。

#### 追问5：Agent瓶颈？

目前Agent最大的挑战主要有三个方面。
第一是规划能力。LLM虽然可以进行多步推理，但是复杂任务中仍可能出现步骤错误或者目标偏移。
第二是工具调用可靠性。模型可能选择错误工具、生成错误参数，或者没有正确利用工具返回的信息。
第三是长期记忆管理。随着任务变复杂，历史信息越来越多，如何保留重要信息、减少无关上下文是一个问题。
工程上通常通过结构化输出、状态管理、工具校验、RAG和人工反馈等方式提高Agent可靠性。

#### 追问6：Agent中的软约束和硬约束有什么区别？

软约束主要通过Prompt引导LLM按照预期方式决策，例如告诉Agent不要重复调用工具、优先使用某类信息或者在特定情况下选择某个Action。但由于LLM本质上是概率生成模型，Prompt只能降低错误行为出现的概率，不能保证规则一定被遵守。

硬约束则由程序运行时直接保证。例如限制Agent最大执行步数、校验Tool参数、阻止完全重复的Tool Call，或者在某项任务已经完成后禁止再次执行。

因此实际Agent系统通常需要结合两者：LLM负责需要语义理解和动态判断的部分，Runtime负责必须严格满足的执行约束。这样既保留Agent的灵活性，又提高系统的可控性和稳定性。


## K6：LangGraph是什么？为什么Agent需要工作流编排？

### 核心：

LangGraph是一个用于构建有状态Agent工作流的图编排框架。它并不是用来替代LLM、RAG、Tool Calling或者Memory，而是负责组织这些模块之间的执行流程。

一个Agent通常不是简单地调用一次LLM就结束，而是可能经历“判断下一步 → 调用工具 → 获得结果 → 再次判断 → 继续调用工具或生成答案”的多步过程。如果完全通过for循环和大量if/else手动控制，随着工具、状态和异常分支增加，流程会越来越难维护。

LangGraph将Agent执行过程表示成图，其中Node表示具体的处理步骤，Edge表示步骤之间的执行关系，State保存整个工作流执行过程中共享的数据。通过这种方式，可以把Agent的控制流显式表达出来，使复杂的多步骤Agent更容易扩展、调试和维护。

#### 追问1：LangGraph中的Node、Edge和State分别是什么？

Node表示工作流中的一个处理步骤，本质上可以理解为一个接收当前State并返回状态更新的函数。例如Planner、Tool执行、生成最终答案都可以分别设计成Node。

Edge表示Node之间的执行关系。普通Edge表示固定跳转，例如Tool执行完成后重新进入Planner；Conditional Edge则可以根据当前State动态决定下一步，例如Planner输出tool时进入Tool Node，输出generate_plan时进入计划生成Node。

State是整个Graph执行过程中共享的数据载体，用于保存不同Node需要共同访问的信息，例如当前决策、Tool Observation、已经执行过的工具以及最终答案。不同Node不需要直接互相调用，而是通过读取和更新State进行协作。

#### 追问2：为什么Agent中经常存在Planner → Tool → Planner的循环？

因为Tool主要负责执行具体的外部能力，例如查询天气、检索RAG或者搜索Web，但Tool本身通常不负责判断整个用户任务是否已经完成。

Planner首先根据用户需求决定调用哪个Tool；Tool执行后产生Observation；然后将Observation重新交给Planner，由Planner判断当前信息是否已经足够。

如果还缺信息，可以继续调用其他Tool；如果信息已经足够，可以生成最终结果；如果缺少用户输入，也可以进入信息补充流程。

因此Agent通常形成“决策 → 行动 → 观察 → 再决策”的循环，而不是简单执行一次LLM调用。

#### 追问3：LangGraph和普通的if/else工作流有什么区别？

从能力上来说，简单Agent完全可以使用for循环和if/else实现，LangGraph并不是实现Agent的必要条件。

区别主要在工程组织方式。当Agent规模较小时，手写循环更加直接；但随着Node、Tool、状态、异常处理和分支不断增加，所有控制逻辑集中在一个函数中会逐渐难以维护。

LangGraph把这些流程显式建模为Node、Edge和State，使控制流和业务逻辑分离。例如Planner只负责决策，Tool Node只负责工具执行，而Graph负责决定它们之间如何跳转。

因此LangGraph的价值主要体现在复杂Agent的工作流编排、状态管理和可扩展性，而不是让LLM本身变得更智能。

#### 追问4：Graph State和Conversation Memory有什么区别？

Graph State主要描述一次工作流执行过程中的运行状态，例如当前Planner决策、Tool返回结果、已经执行过哪些Tool以及最终输出。

Conversation Memory主要保存跨轮对话需要持续保留的用户信息和历史上下文，例如用户之前已经提供的旅行目的地、预算和偏好。

两者生命周期和职责不同。Graph State更偏向Workflow Runtime，而Conversation Memory更偏向跨轮业务状态。

实际Agent系统中两者可以结合使用：先从Memory恢复用户长期或跨轮状态，再将当前任务需要的信息放入Graph State，由Graph完成这一轮工作流执行。
